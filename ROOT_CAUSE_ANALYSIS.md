# ROOT_CAUSE_ANALYSIS.md — Document ID "None" Bug

**Date:** June 19, 2026
**Severity:** Critical
**Status:** Fixed and verified

---

## Symptom

After uploading a document, the frontend receives `document_id = "None"` (the string literal), causing:
- `GET /api/v1/documents/None/jobs` → 404
- All downstream engines fail
- User sees empty dashboard

---

## Root Cause

### Python's `str(None)` = `"None"`

In `backend/app/api/routes/documents.py:43-48`:

```python
created = document_service.create_document_record(doc_payload)
return DocumentMeta(
    id=str(created.get("id")),  # ← If "id" key missing, this becomes "None"
    ...
)
```

In `backend/app/services/document_service.py:28-38`:

```python
try:
    res = requests.post(url, json=[doc], headers=headers, timeout=10)
    if res.status_code in (200, 201):
        data = res.json()
        if isinstance(data, list) and data:
            return data[0]  # ← Returns dict WITH "id"
    return doc  # ← FALLS THROUGH: returns input dict WITHOUT "id"
except Exception as e:
    return doc  # ← Returns input dict WITHOUT "id"
```

### Failure Chain

1. Supabase insert fails (timeout, network error, large payload, etc.)
2. `create_document_record()` catches the error
3. Returns the input `doc` dict — which has **no `id` field** (that's generated by Supabase)
4. `created.get("id")` returns `None`
5. `str(None)` produces the string `"None"`
6. Backend responds with `DocumentMeta(id="None", ...)`
7. Frontend receives `{ id: "None" }` and navigates to `/dashboard/document/None`
8. `useDocument("None")` calls `getDocumentJobs("None", token)`
9. Request hits `GET /api/v1/documents/None/jobs`
10. Backend can't find document with `id = "None"` → 404

---

## Why It Happened Intermittently

The bug only manifested when:
- Supabase was temporarily unavailable (network glitch)
- The `parsed_json` payload was too large for the REST API timeout
- The Supabase service role key had expired or was misconfigured
- Concurrent requests caused connection pool exhaustion

When Supabase was healthy, the insert succeeded and returned a valid UUID, masking the bug.

---

## Fix Applied

### Fix 1: `document_service.py` — Always return dict with `id`

```python
import uuid

# In create_document_record():
    except Exception as e:
        print(f"ERROR: create_document_record exception: {e}")

    # Always return a dict with an id — even if Supabase insert failed
    doc.setdefault("id", str(uuid.uuid4()))
    return doc
```

### Fix 2: `documents.py` — Validate ID before returning

```python
doc_id = created.get("id")
if not doc_id:
    raise HTTPException(status_code=500, detail="Failed to create document record: no ID returned")

return DocumentMeta(
    id=str(doc_id),
    ...
)
```

---

## Prevention

1. **Never use `str(optional_value)` without null check** — Python converts `None` to `"None"` silently
2. **Always validate returned IDs** before using them in responses or navigation
3. **Use `setdefault` or explicit checks** when dealing with auto-generated fields
4. **Two-layer defense**: Service layer generates fallback ID, route layer validates it exists
